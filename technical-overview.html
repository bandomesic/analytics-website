TECHNICAL OVERVIEW
Architecture snapshot · September 2026. Phases 1–6 and source-level hardening are implemented. All domains below are illustrative.

For the technical product owner

One platform. Multiple websites.

A self-hosted analytics application with a small script on each customer website. The websites keep their existing hosting. The analytics platform owns collection, processing, reporting and access control.

03

A pageview’s journey

Collection pipeline Implemented

Observe in the browser

A separate TypeScript tracker captures allowed pageview fields. A bounded in-memory queue batches events and assigns event UUIDs for retry deduplication.

Validate at the application boundary

Check site identity, schema, size, time bounds and allowed properties. Strip fragments, unapproved query parameters and obvious personal data before durable queue serialization.

Derive only the required dimensions

Perform bounded request-time processing for coarse geography, visitor estimation and bot signals. Raw IP must not enter durable jobs or failed-job records.

Process sanitized jobs

Redis buffers work; Horizon workers consume it. Revalidate at the storage boundary, deduplicate event UUIDs and write to monthly PostgreSQL event partitions.

Build and display reports

Idempotent hourly/daily rollups produce rebuildable aggregates. Query objects return report DTOs to Livewire views and a replaceable chart adapter.

What this means for the product

  • Reports are asynchronous. Collection and aggregation are separate steps; the acceptable freshness target still needs agreement.
  • Visitors are estimates. Identifiers rotate per site/day. Do not promise exact people or a cross-domain identity graph.
  • Retries need a contract. Transport, UUID deduplication and queue recovery are covered by integration tests.
  • Retention is active. Defaults are 90 days for raw events and 25 months for aggregates, with scheduled partition and boundary cleanup.
  • Privacy is bounded, not absolute. Automated redaction has limits; purposes, notices and consent requirements need deployment-specific review.
Today: the tracker sends privacy-filtered batches and the application produces aggregate reports. The stakeholder demo remains fictional and disconnected.
04

How the visual designer crosses domains

Authorized editing on the real website

No iframe requirement and no designer payload for normal visitors.

Implemented handshake

1 / Dashboard

Authorize a limited session

A signed-in member selects a site. The dashboard issues a short-lived, single-use code bound to the user, site and target origin.

2 / Customer origin

Exchange the code

Prefer fragment transport, immediately scrub the fragment, then exchange the code for a limited designer session. Never pass the dashboard session cookie or normal credentials to the customer website.

3 / Design & test

Select, test, version

Load a separate designer bundle. Favor stable analytics attributes; resolve multiple matches explicitly. Keep test events separate and preserve earlier published rule versions.

Security boundary: exact origin checks, single-use code exchange, expiry, policy rechecks and test-event isolation are implemented and tested. Deployments should validate compatibility with their website CSP.
05

How the software will be built

Application

Laravel monolith

PHP 8.5 and Laravel 13. Shared application code for web requests, queue workers and scheduled jobs. Tenant policies remain the access boundary.

Reporting interface

Livewire + Blade

Livewire 4, Blade and Tailwind 4. Query → DTO → component boundaries separate data retrieval from presentation. ECharts runs behind a replaceable chart adapter while tables retain the accessible data contract.

Website integration

Small browser bundle

TypeScript with browser-native APIs, built separately with esbuild. The tracker has a 10 KB gzip budget check; designer code remains a separate bundle.

Testing approach in the repository: Pest covers application behavior and tenant boundaries on PostgreSQL; Vitest covers tracker logic; Playwright covers browser flows. The suites include hostile-payload, retry, deduplication, cross-origin and authorization coverage.
06

From repository to deployment

Initial deployment sequence

Choose host, domain and owner

Provision a Docker-capable host and point the analytics domain’s A/AAAA records to it. Choose Caddy or the existing reverse proxy, not both on the same public ports.

Configure secrets and HTTPS

Set APP_URL and APP_DOMAIN, create the application key, database password and setup token, enable secure cookies and trust only the actual proxy source. Caddy requires reachable TCP ports 80/443 for the documented setup.

Start the application stack

Compose starts PostgreSQL and Redis, runs migrations through the init service, then starts app, worker and scheduler services. The Caddy overlay supplies the public HTTPS entry.

Claim the installation

Use the secret setup token to create the administrator, organization and first site. Setup closes permanently after successful completion. Install the site snippet to begin collection.

Verify before onboarding traffic

Check login, tenant isolation, service health, proxy/cookie behavior, restart persistence and restoration. Then validate collection with a controlled website fixture.

Operating responsibilities

  • Exposure: publish the proxy only. The base application port is bound to loopback; PostgreSQL and Redis have no public host ports.
  • Persistence: retain PostgreSQL, Redis AOF, app storage and Caddy state volumes. Redis is not the permanent analytics database.
  • Backups: keep encrypted, access-controlled copies of PostgreSQL, private storage and matching environment secrets off-host; test restoration.
  • Monitoring: cover queue delay, scheduler heartbeat, service health, disk space and database/Redis persistence. The administrator dashboard reports ingestion failures, queue backlog, storage and maintenance freshness.
  • Updates: build versioned application images, apply reviewed migrations and reload workers. Follow the documented upgrade and restoration runbooks.
  • Scaling: start with measured traffic. Moving database/Redis off-host or adding workers requires capacity tests and a private network/authentication design.
Current verification gap: Compose configuration was validated, but the repository records an unresponsive local Docker daemon. Container builds, public TLS, health and named-volume restart behavior still need verification on a healthy Docker host.
