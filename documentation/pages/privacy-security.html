Trust boundary

Privacy and security

Privacy Analytics minimizes browser collection by design and keeps deployment control with the operator. This page describes the technical boundary precisely so teams can make informed policy, consent, access, and retention decisions.

!

Self-hosting and data minimization do not automatically make a deployment compliant with every law. Review purpose, notice, consent, hosting location, access, and retention with the people responsible for privacy in your organization.

What is discarded

  • URL fragments and all query parameters except the five controlled UTM fields.
  • Full referrer paths, queries, and fragments.
  • Raw IP addresses and raw user-agent strings before durable queueing.
  • Form values, element text, link text, and complete outbound destination URLs.
  • Properties with suspicious personal-data keys, email-shaped values, nested objects, or unsupported types.

The supplied Nginx container disables access logging. Review the logging configuration of any reverse proxy in front of the app so request bodies, designer tokens, and sensitive query strings are not added elsewhere.

Visitor and session estimates

Visitor counts use site-specific HMAC-derived values based on transient network and browser inputs. Daily visitor estimates rotate, while a separate cohort estimate supports retention analysis. Sessions are short-lived mappings with a 30-minute timeout.

These values estimate browsers and visits. They are not accounts, durable people profiles, or a reliable way to identify one person across devices.

Browser storage

The public tracker sets no cookies and does not use local storage or session storage. Events wait only in memory until sent. If every lifecycle transport fails while a page closes, the event may be lost; the app accepts that tradeoff instead of creating a persistent browser queue.

The authenticated dashboard uses a first-party Laravel session cookie. Administrator and member accounts are operational application data and are separate from visitor analytics.

Site and origin boundary

Each site is registered with one exact origin. Browser collection requests are accepted only for that site and origin. The Visual Designer also checks the origin before exchanging its short-lived launch code.

Use separate sites for production, staging, and other origins. Copying one site's snippet to another origin should fail instead of merging unrelated traffic.

Internal and automated traffic

Site managers can configure exact IP addresses or CIDR ranges for offices and VPNs. The address is compared transiently and then discarded; the durable event contains only an internal classification. Standard reports exclude internal traffic by default.

Bot and monitoring detection reduces the user agent to bounded classifications and reasons. Confirm TRUSTED_PROXIES when deploying behind a reverse proxy, because a wrong client address weakens internal and traffic-quality classification.

Retention controls

Raw events default to 90 days and daily aggregates to 25 months. Configure these periods with RAW_RETENTION_DAYS and AGGREGATE_RETENTION_MONTHS. The scheduled retention job removes expired raw partitions, deduplication records, old hourly rollups, and expired daily aggregates.

# Preview the retention plan
docker compose exec -T app php artisan analytics:retention

# Apply it immediately
docker compose exec -T app php artisan analytics:retention --execute

Use the preview before changing retention or running the command manually. Backups can retain data longer than the live system, so align backup expiration with the same policy.

Access and infrastructure

  • Serve the application only over HTTPS and enable secure session cookies.
  • Keep PostgreSQL, Redis, and the internal application port off the public internet.
  • Protect .env, backups, connected-source credentials, and dashboard share passwords.
  • Give external database users read-only access to selected reporting views or tables.
  • Review organization membership and revoke unused public dashboard shares.
  • Preserve APP_KEY; it protects encrypted application values such as source credentials.

Operator review checklist

  1. Define the purpose.

    List the product and business questions that justify each event and property.

  2. Review notices and consent.

    Decide what your jurisdiction, audience, and collection choices require.

  3. Set access and retention.

    Keep only the team members and history needed for those purposes.

  4. Test the boundary.

    Inspect browser requests, reverse-proxy logs, exports, backups, and custom event code.

  5. Revisit changes.

    Repeat the review when adding events, sources, recipients, or integrations.
