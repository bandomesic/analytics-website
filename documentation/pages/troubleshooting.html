Problem solving

Troubleshooting

Start with service health and recent logs, then narrow the problem to the web process, queue, scheduler, tracker, mail delivery, or connected source. The checks below follow the same path data takes through the system.

Run these checks first

docker compose ps
docker compose logs --tail=200 app worker scheduler
curl --fail http://127.0.0.1:8080/health
docker compose exec -T app php artisan analytics:check

Every long-running service should be up and healthy. The public health endpoint verifies required application dependencies; the authenticated System health page adds collection, aggregation, conversion, source, queue, and scheduler context.

Containers do not become healthy

  • Read docker compose logs init. Application services wait for the initializer to complete migrations.
  • Confirm DB_PASSWORD, APP_KEY, and other required values exist in .env.
  • Check free disk space and memory with host tools. PostgreSQL may refuse to start when storage is full.
  • Make sure another service is not using APP_PORT.
  • After correcting configuration, run docker compose up -d --build again.

Database authentication fails

Read initializer logs before increasing deployment timeouts. PostgreSQL creates users only on the volume’s first startup; current environment values do not rename users or reset passwords. Use the original credentials or follow the Forge database recovery steps. Do not delete tables or volumes. Errors mentioning MySQL indicate the wrong deployment path or an older configuration.

Installer rejects the setup token

Run the command from the repository directory containing the active .env file:

grep '^SETUP_TOKEN=' .env

Copy only the value after the first equals sign into the installer form. Do not include quotes unless they are part of the value. If setup was already completed, the installer is permanently closed and normal sign-in should be used.

Tracker does not connect

  1. Confirm the snippet.

    Use the snippet from this exact site and verify that tracker.js loads successfully in browser developer tools.

  2. Check the registered origin.

    Scheme, host, and port must match exactly. https://www.example.com and https://example.com are different origins.

  3. Inspect the batch request.

    Look for POST /api/v1/batch. A browser-origin or validation error points to site configuration or event shape.

  4. Check the worker.

    If requests succeed but reports remain empty, inspect worker logs and the queue heartbeat.

  5. Allow processing time.

    Realtime data arrives before hourly and daily aggregate reports.

A custom event is missing

Confirm the event name matches the allowed pattern and that the call runs after the tracker is available. Remove personal-data fields, nested objects, arrays, and non-finite numbers. Test with a minimal event:

window.privacyAnalytics?.track('docs_test', {
    source: 'manual',
    count: 1,
});

For visual rules, confirm the rule is published, its page-path condition matches, and the selector still matches the intended element. “No recent matches” is not proof that a selector is broken; the element may simply have received no qualifying traffic.

Reports are empty or stale

  • Check the selected date range and whether the current UTC day is complete.
  • Review traffic-quality filters and internal-network configuration.
  • Verify the worker and scheduler heartbeats in System health.
  • Run the rollup manually when recovering from downtime:
docker compose exec -T app php artisan analytics:rollup

The rollup is idempotent. Use --site, --from, and --to for a deliberate historical rebuild after reviewing command help.

Emails do not arrive

  • Check that MAIL_MAILER is a delivery transport rather than log.
  • Use Email previews to separate rendering from transport problems.
  • Inspect worker logs because alerts and reports are queued.
  • Confirm the scheduler is healthy; alerts run hourly and scheduled dashboards are evaluated daily.
  • Check provider authentication, sender verification, suppression lists, and spam placement.

An external source fails

For PostgreSQL or MySQL, test connectivity from the analytics server rather than from your laptop. Confirm DNS, port, firewall rules, TLS requirements, database name, and read-only permissions. The source user needs access to each reporting table or view you expose.

For CSV files, verify the 5 MB and 100,000-row limits, unique headers, and stable columns. Replacing a CSV fails when the new file removes a column already used by a metric.

If a connection succeeds but a metric is wrong, inspect the source rows, date column, numeric type, aggregation, filters, and calculated formula. Connection health proves reachability, not business meaning.

HTTPS links, redirects, or login behave incorrectly

Set APP_URL to the public HTTPS URL, enable SESSION_SECURE_COOKIE=true, and configure TRUSTED_PROXIES for the actual reverse proxy address. Ensure the proxy forwards Host, X-Forwarded-Proto, and X-Forwarded-For.

If CSS and scripts are blocked as mixed content, follow the Forge HTTPS proxy steps. Save the environment and redeploy to recreate containers and refresh cached configuration, then hard-refresh the browser.

The old interface remains after deployment

Rebuild the production image or frontend assets and refresh Laravel caches:

docker compose build --pull
docker compose up -d --remove-orphans
docker compose exec -T app php artisan optimize

Then perform a hard refresh in the browser. A native installation must run npm ci && npm run build during deployment.

Safe recovery boundaries

!

Do not run docker compose down -v, regenerate APP_KEY, delete PostgreSQL files, or restore over the live database while diagnosing a problem. Take a backup and understand the failure first.

For backup, restore, upgrade, and retention procedures, continue to Production operations.
